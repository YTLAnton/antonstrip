# Sprint Intake Brief — 需求簡報 / Sprint 啟動表

> ⓘ **「intake」一詞解釋**：英文業界詞，意思是「把模糊想法收進來變成清晰需求」。中文叫「需求簡報」或「Sprint 啟動表」都可以——本檔以下統一用「intake」。
>
> **用途**：把你腦袋裡那 1~4 句模糊的想法，擴展成 Planner 能規劃的完整需求簡報。
> **填寫者**：你（Anton 或專案負責人）
> **預估填寫時間**：**5~10 分鐘**（v0.6 瘦身後——比 v0.5 少一半）
> **下一步**：填好之後 `/harness:planner` 會讀這份，產出 `plan.md` + `contract.md`
>
> ⚠️ 本檔是**空白模板**。實際使用時請複製到 `{sprint-dir}/intake.md` 再填。

---

## 📝 PDM 寫法引導（v0.6 必讀）

寫 intake 時記住三句話：

1. **「我媽看得懂嗎？」自我檢查**——每段寫完問自己「不是技術背景的人讀得懂嗎？」如果不行，改寫白話版本。
2. **不知道就空著，Planner 會問**——下方 optional 欄位真的可以全空。Planner 看到空欄會主動發問澄清，不是預設默許。
3. **白話優先於精確**——「啟動時點搜尋會被打斷」比「初始化階段 race condition」好懂。Planner 翻譯成技術語言是它的工作。

> 第一次填？不確定有沒有「填對」？沒關係——填得不完整 Planner 會問。但「**動詞 + 對象 + 期待結果**」這個句型一定要練。

## Sprint Metadata（必填，6 個 YAML 欄位）

```yaml
sprint_id: sprint-001-pwa-install-prompt
project: antonstrip
adapter: content-site
mode: production
track: dual
created_at: 2026-05-20
created_by: Anton
```

### `track` 欄位：sprint 位置宣告（🆕 v0.6 新增）

這個欄位告訴 Planner「本輪 sprint 的工作檔該開在哪裡」。三選一：

| 值 | 意思 | 何時用 |
|---|---|---|
| `pilot` | **中央試點軌**：sprint 開在 `Harness/pilots/0X_*/sprint-NNN/` | 純粹是要試 Harness 自己（不是要修真實專案）|
| `real` | **真實使用軌**：sprint 開在 `{project}/_PM/harness/sprint-NNN/` | 日常工作（真的要改 / 評估 / 規劃某專案）|
| `dual` | **雙軌制**：兩處都有（中央版做對照、真實版做工作） | 試點階段（Phase 4~6）、首次跑某專案、要把試點結果回灌中央 retrospective |

> **不確定就選 `real`**。Phase 4~6 試點階段預設 `dual`。

> 📝 **答案區（直接編輯下方框內文字）**

```text
為手機看行程的旅客加上「裝到主畫面」提示，可一鍵裝、可關閉不再現
```

> ⚠️ **強制限制**：不超過 30 字。逼你想清楚到底要做什麼。

**句型**：「**動詞 + 對象 + 期待結果**」

✅ **好範例**
- 修復 AAABAO 啟動 race condition，讓首三秒操作不再被打斷
- 為 FTMO-Bridge 建立上線就緒檢查清單（10~20 項可勾選條件）
- 為 antonstrip 設計圖片插入捷徑（從 `image: name.jpg` 自動組路徑）

🚫 **壞範例**
- 「提升品質」（→ 沒指對象、沒指改善方向）
- 「修一些 bug」（→ 哪些？驗收標準在哪？）
- 「優化使用者體驗讓系統更穩定更現代化」（→ 太多形容詞、沒一個可驗）

如果該專案的 baseline.html 有 W-XX 痛點清單，**最好直接點名**——例如「W-01 啟動 race condition」。沒有 baseline 也沒關係，用白話描述真實感受到的痛即可。

✅ **好範例**

🚫 **壞範例**
- 「該修了」「想做」（沒交代為什麼）
- 「品質不夠好」（→ 哪裡？怎麼樣才算夠好？）

## Optional 欄位（4 個——不知道就空著，Planner 會問）

> ⚠️ **以下都是 optional**。空著沒關係，Planner 看到空欄會主動發問澄清。但若你心裡有畫面，主動填能讓 Planner 規劃更準確。

### ④ 使用者 / 受眾（optional）

> 📝 **答案區（直接編輯下方框內文字 — 可空）**

```text
- 旅遊中的旅客（手機開行程網頁的人，含我自己）：在飛機/陌生地網路差時，PWA 裝在主畫面可以離線快速開啟
- 分享行程連結的收件人：朋友/家人收到 URL 點開，看到提示後可選擇裝起來追蹤行程
```

> ℹ️ 我把你原本「所有觀看者」**拆成兩種具體受眾**，每種附一句「為什麼這次改動對他有用」。
>
> 不滿意？直接改 code block 內文字。

---

**填寫提示**：「這次改動的受益者是誰？」可以是：
- 真實使用者（誰會看到、用到、被影響？）
- 你自己（哪一面：寫 code 的你？營運的你？對帳的你？）
- 未來的合作者（要交接給某人？）
- 系統本身（這次是給後續開發、後續測試打地基？）

**寫法**：列出**最多 3 種**受眾，每種附一句「他們會怎麼感受到這次改動」。

🚫 **壞範例**：「使用者」（→ 哪種使用者？做什麼的使用者？）

> ℹ️ 我把你原本寫在 ① 的細節（提示位置、X 鈕、引導教學）**搬到這裡**——這欄就是專門描述「成功時的具體畫面」。
>
> 不滿意？直接改 code block 內文字。

> ⚠️ **不是**列驗收條目。驗收條目是 Sprint Contract 的事，這裡是**畫面**。

**填寫提示**：用 1~3 段敘事，描述這個 Sprint 完成後，**某個具體場景**會如何發生。要有人物、有動作、有時間、有感受。

**句型參考**：「Sprint 結束後，當 {人物} 在 {情境} 做 {動作} 時，{會發生 / 不再發生 X}，他會感受到 {Y}。」

✅ **好範例**
> Sprint 結束後，當我早上一開 AAABAO 想要記錄昨晚的咖啡花費，我能在 app 載入第一秒就直接點下「新增記帳」開始輸入金額，而不會像現在這樣突然介面閃一下、輸入到一半被洗掉。我會像 Google Keep 那樣，相信它不會偷偷打斷我。

🚫 **壞範例**
> 系統變得穩定、UX 更好、使用者更滿意。

**填寫提示**：寫下「**這次 Sprint 範圍外**」的條目。包括：

**寫法**：每條一行，用「**不**……」開頭。

✅ **好範例**

- 不改 design_guide.md（不管 UX 改得多誘人）

🚫 **壞範例**
- 不要做太多（→ 太多是多少？）
- 不要影響其他功能（→ 受影響本來就是壞事，不需要列）

### ⑦ 已知限制（optional）

> 📝 **答案區（直接編輯下方框內文字 — 可空）**

```text
- 靜態網站（GitHub Pages 部署）—— 沒有後端、不能存 server-side 資料
```

> ℹ️ 我幫你列了 4 條技術硬約束——這些是 PWA 在 antonstrip 環境（靜態站、多個 index.html、跨平台手機）會踩到的真實限制。
>
> 不熟技術細節？沒關係——這些是給 Planner 看的，他會處理。但**「靜態站、跨多個 index.html、iOS 跟 Android 不同」這三件事一定要在**，不然 Planner 可能規劃出不可行的方案。
>
> 不滿意？直接改 code block 內文字。

**填寫提示**：影響本次 Sprint 設計的硬約束，**只列你真正知道的**，不要憑空生成。

可以含但不限於：
- **時間**：「希望 X 天內結束」或「最晚 X 日要上線」
- **預算 / 工具**：「不能引入新付費服務」、「只能用既有 stack」
- **法規 / 合規**：「不能存使用者個資 hash 以外的東西」
- **依賴**：「broker API 文件還在等對方更新」

如果**真的沒有**特別限制，留空即可（Planner 會默認「無已知限制」）。

🚫 **壞範例**
- 「要快又好」（→ 不是限制，是廢話）
- 「不能讓系統變慢」（→ 預設就該如此）

## 參考素材（Phase 6 試點新增 — 非模板原生欄位）

> 🆕 **本段為 Phase 6 sprint-001 試用**：Harness v0.6 intake 模板沒有「附件」欄位。本輪試這套做法看順不順、要不要回灌成模板規範（IMP 候選）。

把要參照的素材放在本 sprint 下的 `references/` 子資料夾，並在這裡列出：

**檔名規範**：
- 競品截圖：`competitor-{name}-{what}.png`，例：`competitor-pinterest-pwa-prompt.png`
- 競品 HTML 片段：`competitor-{name}-snippet.html`，例：`competitor-twitter-install-banner.html`
- URL 清單：`reference-urls.md`（一行一個 URL + 一句話為什麼有用）
- 設計靈感圖：`inspiration-{topic}.png`

**素材列表**（每條一句話為什麼附）：
- 'references/image.png' — 就像這樣
- 'references/ex.html' — 提供elements參考
- `references/{檔名}` — {這個做對了什麼 / 我希望像它一樣有 X}
- （依此格式繼續列）

**Planner 與 Generator 行為**：讀完 intake 必看 `references/` 內所有檔案；plan / contract / output 設計可參照這些素材；但**不可直接複製競品 element**（版權與一致性風險）——只能擷取設計概念。

## 給 Planner 的明確指令（這段不要刪）

> Planner，當你讀到這份 intake 後：
>
> 1. **先檢查 metadata 的 `track` 欄位**——決定 sprint 工作檔在哪個位置上開
> 2. **不要直接執行任何改動**——你只負責規劃
> 3. **檢查必填欄位（①②③）是否填齊**——任一空白就停下來問使用者
> 4. **Optional 欄位（④~⑦）若空**，用澄清問題的方式補上——不要默默用預設值；最多問 3 個澄清問題
